# Funti3r-pay

**Blockchain-powered cross-border workforce payments with instant settlement and compliance-by-design**

Funti3r-pay enables enterprises to pay global teams quickly, compliantly, and cost-effectively using Stellar blockchain technology.

## Quick Start

### Prerequisites
- Node.js 18+
- pnpm 9+
- Docker Desktop

### Setup (5 minutes)

```bash
git clone https://github.com/Katlego909/funti3r-pay.git
cd funti3r-pay
cp .env.example .env.local
pnpm install
```

Fill in `.env.local` (see `.env.example` for every variable). The services refuse to start without real secrets, so
generate them, for example with `openssl rand -hex 32`:

- `JWT_SECRET`, `INTERNAL_AUTH_SECRET` (at least 32 characters; the gateway signs the identity it forwards and
  every service verifies it), `MASTER_ENCRYPTION_KEY` (64 hex characters, encrypts wallet keys and KYC data)
- `POSTGRES_PASSWORD` and `REDIS_PASSWORD`: read by Docker Compose itself, so put them in a root `.env` file
  (gitignored) or your shell

```bash
docker compose up -d   # Postgres (host port 5433) and Redis (6379), published on localhost only
```

`docker compose up -d` also loads `docker-compose.override.yml` (local development: publishes the database ports,
runs Redis without a password, turns on testnet KYC auto-approval). Production uses
`docker compose -f docker-compose.yml up -d`, where only the Caddy proxy is reachable from outside.

### Run Services

```bash
pnpm --filter @funti3r/api-gateway dev
```

Other services available:
- `@funti3r/user-service` (port 3001)
- `@funti3r/payment-service` (port 3002)
- `@funti3r/compliance-service` (port 3003)
- `@funti3r/analytics-service` (port 3004)
- `@funti3r/enterprise-dashboard` (port 3100) — unified web app for both enterprises and workers,
  role-based routing after login

Verify: `curl http://localhost:3000/health` (every service also has `/health/live` and `/health/ready`).

> **Tip:** run the dashboard independently (`pnpm --filter=@funti3r/enterprise-dashboard dev`)
> rather than a single root `pnpm dev`, so one backend service crashing doesn't tear down the
> whole group.

### Testnet currency liquidity (for local-currency payouts)

The local African currencies (NGN/KES/GHS/ZAR/UGX) are self-hosted on testnet: an issuer
account issues them and a distributor seeds DEX liquidity at live FX rates so path payments
can route. Run once (and re-run to refresh rates):

```bash
cd services/payment-service
node --env-file=../../.env.local --import tsx scripts/setup-africa-liquidity.ts
```

On mainnet, point the registry at real anchors (e.g. Cowrie for NGN) — no code change.

## What It Does

Funti3r-Pay lets enterprises pay a global workforce on Stellar — fast, low-cost, and in the
currency each worker actually wants:

**Payments**
- **Classic Stellar XLM payouts** — enterprise → worker, signed + submitted on-chain.
- **USDC stablecoin payouts** — exact USDC delivered via strict-receive path payment, funded
  from the enterprise's XLM through the Stellar DEX; worker trustline auto-created.
- **Multi-currency payouts (USD → local)** — the employer sends a **USD** amount and the worker
  receives their **preferred local currency** (NGN, KES, GHS, ZAR, UGX), converted at **live FX
  rates** via Stellar path payments. (e.g. `$10 → 13,766 NGN` settled on-chain.)
- **Batch payouts** — pay many workers in one request, executed sequentially; recorded in
  `payment_batches` with per-payment linkage; returns partial-success (HTTP 207) when some fail.
- **Worker payout-currency preference** — workers choose what they get paid in ("Get Paid In").
- **Stellar transactions are serialized per account** so two simultaneous payouts from one wallet never collide,
  and balances shown in the app are refreshed the moment money moves.

**Milestone escrow (Soroban smart contract)**
- An employer funds an escrow for a worker in milestone tranches. The worker submits work, the employer reviews it
  and approves each milestone (an on-chain transaction), and the worker claims the approved amount straight from
  the contract. Unapproved funds return to the employer after the expiry date.
- **On-chain compliance gate** — `create`, `approve` and `claim` fail unless the worker holds a live clearance
  recorded by the compliance authority, bound to the hash of the screening record behind it. The authority can
  revoke a clearance, freeze one escrow, and return a frozen escrow's unclaimed funds to the employer.
- The backend re-screens the worker before every create, approve and claim, and fails closed if compliance is
  unreachable. Contract code is upgradeable by an admin key (address and storage survive).
- 31 contract tests plus a scripted testnet run; the compiled wasm and its hash are published with each release.

**Cash-out (MoneyGram Ramps)**
- Workers cash out of their wallet balance through MoneyGram: the platform pays USDC to MoneyGram on Stellar and
  MoneyGram issues a pickup reference for cash collection. Runs against the **MoneyGram sandbox**; production needs
  MoneyGram's KYB and certification. Cash-outs show a step-by-step receipt of how the amount was worked out.

**Auth & accounts**
- **WebAuthn / passkey** registration & login (`@simplewebauthn`), plus a **dev login**
  (email-only, non-production) so local testing doesn't require a passkey.
- Each user gets a **classic Stellar ed25519 account** at registration, auto-funded on testnet
  via Friendbot. **Secret keys are encrypted at rest** (AES-256-GCM).

**Compliance**
- KYC submit/status/approve/reject, scoped to the worker's own company, with submissions **encrypted at rest** and
  every decision written to an audit trail. Approvals expire and can be re-submitted.
- **Sanctions screening against the real OFAC SDN list**, refreshed and re-screened daily (new matches revoke access),
  with word-order, middle-name and typo tolerance and year-of-birth matching so namesakes are not flagged.
  Employers are screened before they fund an escrow.
- An **auto-approve mode** for testnet (`COMPLIANCE_AUTO_APPROVE=true`); a sanctions match always forces a rejection.
- The worker's KYC page shows what the escrow contract itself holds for them (clearance, expiry, screening hash).

**Dashboard (React + Vite, port 3100)**
- One landing page, one login/register flow, role-based routing after auth — no separate apps.
- **Enterprise** view: send single/batch payments, create and approve milestone **escrows**, worker
  directory + KYC view, wallet balances, payment list, and **insights charts** (volume over time, payments by status).
- **Worker** view: balances (XLM + USDC + any local currency) shown in one chosen currency, escrow milestones
  (submit work, claim), MoneyGram cash-out, payment history, KYC, payout-currency selector, and **insights charts**.
- **CSV and PDF export** of payments, escrow milestones and cash-outs; payslips for each payment.
- A public **`/proof` page** listing the contract, its code fingerprint and the testnet transactions.
- **Correct multi-currency valuation** — totals and charts convert each currency to USD with
  live rates (no naive cross-currency summing).
- **Live pricing** — XLM/USD (CoinGecko) and USD→fiat (open.er-api.com) feeds.

## Security & operations

- **Only the edge proxy is reachable from outside** (Caddy, automatic HTTPS). The gateway, services, Postgres and
  Redis stay on an internal network; containers run read-only with all capabilities dropped.
- **Gateway-signed identity** — services trust a forwarded identity only if its HMAC signature checks out, so a
  direct call to a service with forged headers is rejected.
- **15-minute access tokens**, httpOnly refresh cookie, passkeys (WebAuthn); no built-in JWT secret in any
  non-test environment. **Request bodies and ids are validated** with zod at every route boundary.
- **Rate limits** per client, with tighter per-user limits on money-moving routes (Redis-backed).
- **Backups with a restore drill** (`scripts/ops/backup.sh`, `restore.sh`, `restore-drill.sh`), versioned encryption
  keys and a rotation script (`services/payment-service/scripts/rotate-keys.ts`), and a database guard that refuses
  to delete financial records.
- **Observability** — structured JSON logs with request ids, Prometheus `/metrics` on every service, readiness checks, alert
  rules (`deploy/alerts.yml`), and one append-only audit table for every action that moves money.
- **CI** (GitHub Actions): type-check, lint, build and tests; dependency audit and secret scanning; a backup/restore
  drill; and the contract's tests plus a wasm build that publishes the wasm and its SHA-256 on every version tag.

## Architecture

**Microservices:**
- **API Gateway** - Request routing & authentication
- **User Service** - User management & authentication
- **Payment Service** - Stellar blockchain integration
- **Compliance Service** - KYC/AML & audit trails
- **Analytics Service** - Metrics & reporting

**Frontend:**
- **Web app** (React + Vite): a single app for both roles, with role-based routing after sign-in

**Data:**
- PostgreSQL - Transactional data & analytics
- Redis - Caching & sessions

**Blockchain:**
- Stellar Network (testnet & mainnet)
- Soroban escrow contract ([`contracts/escrow`](contracts/escrow)) with an on-chain compliance gate

**Edge & observability:**
- Caddy reverse proxy (TLS) in front of the gateway; Prometheus is available as an optional `monitoring` profile

## Technology Stack

**Web app**
- React 18 + TypeScript, built with Vite 5
- React Router, Zustand (state), Recharts (charts), Sonner (notifications), jsPDF (PDF exports)
- WebAuthn passkeys in the browser (`@simplewebauthn/browser`)
- Stellar JS SDK 16

**Backend** (microservices behind an API gateway)
- Node.js 20 (18+ supported) + TypeScript (strict, ESM), Express 4, run with `tsx`
- zod request validation, helmet, express-rate-limit with a Redis store
- Passkey authentication (`@simplewebauthn/server`), short-lived JWT access tokens
- PostgreSQL 16 (`pg`) with SQL migrations applied at service start, Redis 7
- Stellar JS SDK 16 (Horizon and Soroban RPC), MoneyGram Ramps (sandbox) for cash-out

**Smart contracts**
- Rust + Soroban SDK 29, built with the Stellar CLI to `wasm32v1-none`

**Infrastructure & operations**
- Docker Compose (read-only, non-root containers), Caddy 2 reverse proxy with automatic HTTPS
- Prometheus metrics (`prom-client`), structured JSON logs
- Terraform (AWS) as a deployment starting point
- GitHub Actions CI: type-check, lint, build, tests, dependency audit, secret scanning, contract build

**Tooling**
- pnpm 9 workspaces with Turborepo 2
- ESLint, Prettier, Vitest, Node test runner, `cargo test`
